# ArticleHarvest → PressDock 迁移计划（后台采集与自动提交版）

更新日期：2026-10-26（Asia/Shanghai）

状态：已按计划实施代码；验证结果与尚待实机核验事项见 README 和本次交付说明。

## 1. 本轮已确定的产品流程

1. **复用现有“素材导入”页面和路由。** 输入单个文章链接，点击按钮或按回车，调用同一个提交入口。
2. **提交链接后立即创建本地任务，后台采集。** 输入框下显示任务列表，页面不等待整篇采集完成才返回。
3. **列表固定两列：“标题”“状态”。** 点击标题打开提交 URL 的原文，不跳转编辑器或 CMS 文章地址。
4. **采集、格式化和自动处理完成后，直接提交 CMS。** 这轮不增加正文预览、分页预览、手工编辑或“确认后提交”步骤。
5. **SQLite 保存采集数据和状态，保留历史。** 列表默认只显示当天，可按日期查看历史。
6. **设置页可配置历史保留时间，应用启动时执行清理。** 这是你已补充确认的规则。
7. 保留上一轮要求的五项开关，以及 ArticleHarvest 的来源适配、格式化、AI 处理、分页和失败回退规则。

本文的“后台”指 **PressDock 的 Rust 应用后台任务**。CMS 接收最终处理后的文章；不假设 CMS 已有接收 URL 后远程爬取的接口。任务在应用运行期间执行，离开素材导入页仍继续；完全退出应用后停止，下一次启动按恢复规则处理。

## 2. 素材导入页：输入表单 + 当天记录

### 2.1 复用现有入口

复用 `src/pages/Import/index.tsx` 的页面、URL 输入、表单提交及错误反馈。当前演示创建入口改为真实任务入队；现有 `form onSubmit` 同时承接按钮和回车，不另写两套采集触发逻辑。[P3]

交互顺序：

1. 输入 URL，点击 **“开始采集”** 或按回车。
2. 前端校验链接；Rust 再校验来源支持范围、登录状态及请求标识。
3. Rust 读取已保存设置，事务写入一条“排队中”的本地记录，返回任务 ID 和记录。
4. 页面把该记录加入当前日期列表；落库成功后清空输入框、恢复焦点，可继续添加下一个链接。
5. Rust worker 在后台依次处理，列表原位更新同一条记录的标题和状态。

按钮只在“提交入队请求”的短暂阶段禁用，不因已有任务正在采集就持续禁用。入队失败保留输入，且不显示一条假的成功记录。入队提示用“已加入采集队列”，不提前提示“素材添加成功”。

### 2.2 列表严格两列

| 列   | 展示规则                                                                                                                                     |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 标题 | 尚未读到标题时以输入 URL 作为链接文字；采到标题后原位替换。长标题按现有布局换行或截断并可查看完整文本。点击调用现有外链能力打开输入 URL 原文 |
| 状态 | 显示排队、采集、处理、提交及最终结果；失败原因、降级提示、验证继续或重试操作放在本单元格内，不增加操作列                                     |

复用已有 `DataTable` / `useDataTable` 基础能力，在素材导入模块中定义两个业务列；不直接套用带来源、时间、编辑操作的 `ArticleTable`。[P4]

原文链接通过导入业务服务复用已有 `open_external_link` 类型化 IPC 和 Rust 协议校验，由系统浏览器打开；组件仍不直接调用 `invoke`。[P5]

列表按入队时间倒序，新任务在顶部，状态变化不改变行位置。工作台的采集执行顺序仍按入队时间正序，两种排序分别满足查看和执行的需要。

列表上方提供日期选择，默认 **今天**，历史查询不增加表格列。新任务始终归属当前入队日期；正在查看历史日期时，新任务入队成功后切回今天，确保新记录可见。重复链接定位历史已有记录时，则切换到该记录所属日期。空列表显示“今天暂无采集记录”或对应日期的空状态。

### 2.3 状态更新与页面切换

任务状态先写 SQLite，再通知页面刷新；通知不是持久化来源。进入页面先订阅刷新通知，再加载 SQLite 快照；后续通知触发读取最新记录，页面返回时重新查库，不只依赖之前的前端内存。离页释放通知订阅，不释放后台任务。

离开页面不取消后台任务，重新进入后继续显示其最新状态。跨过零点后，当天筛选切换到新日期；昨天尚未完成的任务继续运行，可在昨天记录中查看，不因日期变化取消。

## 3. 后台任务与状态流转

### 3.1 执行流程

```text
输入链接，点击按钮 / 回车
  → 校验并持久化任务、所属账号、入队日期和自动处理设置快照
  → 返回“排队中”，输入框可继续提交

Rust 串行 worker
  → 内置 WebView 获取网页
  → 提取标题、作者和正文，采全来源站分页
  → 保存不可变原始素材
  → 调用旧 FormatContent 链建立格式化基底
  → 根据开关生成分类 / 标签 / 摘要
  → 根据开关整理正文 / 本地分页
  → 保存最终待提交 payload
  → 持久化“提交 CMS 中”后发出 Article 请求
  → 收到明确成功响应后持久化“已添加到 CMS”
  → 列表更新最终状态
```

不增加文章结果预览或提交确认。用户点击“开始采集”，即启动这篇链接从采集到 CMS 提交的整条任务；这是本轮已经确定的目标行为，实际实现不应再插入第二次常规确认。

### 3.2 列表状态与含义

| 状态文字        | 含义及后续行为                                                         |
| --------------- | ---------------------------------------------------------------------- |
| 排队中          | 已持久化，等待 worker，尚未开始访问来源                                |
| 采集中          | 正在获取页面或来源后续分页；读到标题后立即更新标题                     |
| 等待网页验证    | 需要在来源 WebView 登录或验证；状态格提供打开来源窗口、继续和取消      |
| 格式化中        | 正在执行后台 FormatContent                                             |
| 生成元数据中    | 正在生成已开启的分类、标签、摘要；三项全关时跳过                       |
| 整理正文中      | 仅在自动正文整理开启时出现                                             |
| 内容分页中      | 仅在自动内容分页开启时出现；只分页不调用 AI                            |
| 提交 CMS 中     | 最终 payload 已保存，文章创建请求正在执行                              |
| 已添加到 CMS    | 明确收到符合成功契约的响应并记录结果；需要时在同一状态格附 AI 回退提示 |
| 失败            | 已知失败，记录失败阶段和简短原因；允许对确定未成功提交的阶段重试       |
| 等待重新登录    | CMS 登录失效，停止后续远程动作，等待原账号恢复                         |
| 已中断 / 已取消 | 应用中断或用户取消；保留已经持久化的数据，不误报完成                   |
| 提交结果待确认  | 请求可能已被 CMS 执行，但客户端无法确认；不自动重发                    |

实现中使用任务状态和处理阶段表达这些信息，避免用多个互相矛盾的布尔值拼状态。错误与警告是本地字段，不进入 Article payload。

首期一个 worker 串行处理整篇，支持连续输入形成队列，不增加并发采集。遇到网页验证时保留当前 WebView 页面，当前任务等待，后续任务继续排队；用户取消该任务后再处理下一篇。任务明确失败、已取消或进入提交结果待确认后，worker 可以继续处理后续不同链接；等待验证或重新登录时暂不推进当前任务。

### 3.3 去重、取消与重试

- 同一次表单提交使用稳定请求 ID，重复点击、回车或 IPC 结果丢失后的同请求重试，只能创建一条任务。
- 对**本地保留期内**同账号、规范化 URL 的排队/处理中/已成功记录去重；忽略片段，保留有效查询参数。重复提交定位已有记录并显示状态，不重新发出 CMS 请求。跨天不解除这一去重。
- 对确定失败且未提交成功的记录，在原记录上重试；保留入队日期及设置快照，记录尝试次数。格式化失败可复用已采原文，CMS 明确拒绝后的重试可复用最终 payload，不默认重新调用 AI。
- 已成功记录不自动重采重发。删除历史后，本地去重依据也会消失；是否能由 CMS 提供长期查重能力，待真实接口核实，不承诺全历史唯一。
- 取消采集/处理只取消本篇，不关闭用户系统浏览器。CMS 请求已发出后取消，不能断言远端撤销；结果未知时进入“提交结果待确认”。

## 4. 本地数据、当天归属及历史保留

### 4.1 存储内容与复用范围

继续使用 SQLite，并新增必要的 **采集任务记录 `harvest_jobs`**。任务先落库，再交给 worker；不把持久队列只存在 Jotai、组件状态或 localStorage。

| 数据组     | 持久化内容                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------------- |
| 任务身份   | 任务 ID、入队请求 ID、创建任务的 CMS 用户 ID                                                       |
| 来源与列表 | 输入 URL、规范化 URL、最终 URL、已提取标题、作者、采集日期                                         |
| 执行状态   | 状态、阶段、错误/警告、尝试次数、创建/更新/完成时间                                                |
| 任务设置   | 入队时的五项开关和模型配置 ID；不复制密钥                                                          |
| 原始素材   | 复用 `source_articles` 保存不可变原文，任务通过 `source_id` 关联；必要时补充 HTML 格式及来源元数据 |
| 处理结果   | 与原文独立的格式化结果、最终待提交 payload；提交前必须保存                                         |
| CMS 结果   | 请求发起时间、结果确认时间、可确认的响应摘要及接口实际返回的文章 ID（若存在）                      |

本轮不为每篇任务自动创建 `drafts` 编辑稿件，也不扩展编辑器。既有 `source_articles` / `drafts` 的分离和原文不可覆盖规则继续保留；未来需要将任务转入编辑时再按现有机制创建独立草稿。

新增 SQLx 迁移，不修改已执行迁移。已有演示文章及其读取行为保持兼容，真实任务不带演示成功标识。

### 4.2 当天与历史日期

- “当天记录”按**任务提交入队时的本地日期**归属，不按原文章发布时间或最终提交完成时间归属。
- 实际时间戳存 UTC，另存入队时计算出的本地 `collection_date` 与当时时区信息；本次环境为 Asia/Shanghai。
- 例如 10 月 26 日 23:59 入队，10 月 27 日 00:05 完成，仍属于 10 月 26 日记录。
- 当天查询按当前系统本地日期筛选；历史记录的入队日期不因重启或系统时区变化重算。
- 默认查询当前账号 + 今天。历史日期查询也按任务所属账号过滤，防止换号后把旧任务提交到另一个 CMS 账号。

任务按账号归属只作用于新采集队列和历史记录，不借此扩展为整个现有本地稿件库的多账号改造。

### 4.3 历史保留时间与启动清理

你已确认：**保留历史，列表默认当天；保留时间在设置页配置；软件启动时触发清理。**

建议的具体规则：

- 在“采集与自动处理”设置增加“历史保留时间”：默认 **永久保留**，可改为 **保留 N 天**，N 为正整数。
- 保留 N 天表示按本地日历日保留最近 N 个入队日期，包含启动当天。例如 10 月 26 日设置保留 7 天，保留 10 月 20～26 日，清理 10 月 19 日及更早的符合条件记录。
- 修改设置只保存规则，下次启动执行；首期不增加定时清理或手动清理按钮。
- 启动时完成数据库初始化及迁移，读取保留设置，执行一次清理，再恢复任务调度；清理操作不需要调用 CMS。
- 仅清理超过保留期且处于 **已添加到 CMS、失败、已取消** 等明确终态的记录。
- 排队中、等待验证/登录、处理中、已中断和提交结果待确认的记录暂不自动删除；进入明确终态后再按规则处理。
- 清理同时删除该任务的专属处理结果和待提交快照。仅当原文确由采集任务创建，且已没有其他任务或编辑草稿引用时，才清理对应原始素材；不能误删既有独立稿件。
- 清理范围只在本机数据库，不删除 CMS 文章，也不清除来源 WebView 登录数据。
- 清理事务失败保留原数据并记录提示；应用仍可使用，不将清理失败伪装为成功。

永久保留时跳过按时间删除。清理属于启动生命周期，离开导入页、切换日期或跨过零点都不会触发历史删除。

### 4.4 启动恢复与账号变化

| 启动时发现的状态      | 恢复规则                                                       |
| --------------------- | -------------------------------------------------------------- |
| 排队中                | 先保留，原 CMS 账号认证成功后按入队顺序继续                    |
| 采集/格式化/AI 处理中 | 标记已中断，保留已保存阶段，由用户重试；不自动重复付费 AI 请求 |
| 等待网页验证          | 保留记录；重启后不能假定原 DOM 仍在，按中断记录恢复操作        |
| 提交 CMS 中           | 转为提交结果待确认，禁止开机后自动重发                         |
| 已添加/失败/已取消    | 按本地结果展示，符合保留期条件时清理                           |
| 提交结果待确认        | 保留用于核对，用户确认远端结果前不自动重试或清理               |

离开页面不影响 worker。显式退出或切换 CMS 账号时停止旧账号后续动作，不把其队列交给新账号；已经发出的创建请求仍按实际可确认程度记录结果。

## 5. 系统设置与任务快照

在设置页增加“采集与自动处理”，包含五项开关、一个复用现有 AI 模型的选择项，以及上述历史保留时间。

| 设置项       | 建议初始值 | 开启时                                                 | 关闭时                         |
| ------------ | ---------- | ------------------------------------------------------ | ------------------------------ |
| 自动分类     | 关闭       | 生成并校验 `classId`，有效时覆盖默认分类               | 不请求该字段，沿用默认分类 `1` |
| 自动标签     | 开启       | 生成非空、去重后 3～5 个标签                           | 首次导入为空数组               |
| 自动摘要生成 | 开启       | 生成最多 130 字符的内容简介 `smallText`                | 保留 `FormatContent.smallText` |
| 自动正文整理 | 关闭       | 使用旧原文片段布局、段落整理、图注与允许的首尾清理规则 | 不调用整理模型                 |
| 自动内容分页 | 关闭       | 按旧本地分页算法输出内容分页                           | 不执行新增分页计算             |
| 历史保留时间 | 永久保留   | 设置 N 天后，下次启动按日历日清理符合条件的历史        | 永久保留时不按时间删除         |

五项开关和模型选择存 SQLite，密钥使用现有系统凭据库。入队时固定任务快照，排队期间修改设置只影响新任务；历史保留时间属于应用级规则，不复制到每篇任务快照。

“摘要”仅为旧项目的内容简介，不压缩或替换正文。分类、标签、摘要至少一项开启时发一次合并 AI 请求，只要求启用字段；三项全关时跳过。正文整理独立调用；只开内容分页不调用 AI。

五项全关仍执行后台 FormatContent，再自动提交 CMS。模型未配置或 AI 调用失败时沿用旧回退规则，并把警告保存在任务状态中；不能把跳过或回退写成生成成功。

先复用原元数据/排版提示词和现有提供商、模型、安全密钥能力，不增加新的可编辑任务模板体系，不自动改写标题。

## 6. 复用 ArticleHarvest 的业务规则

| 原模块/规则                      | 迁移处理                                                                                |
| -------------------------------- | --------------------------------------------------------------------------------------- |
| URLParser / config               | 首批百度两个真实入口；规范化匹配，不迁移示例站点为“已支持网站”                          |
| BrowserHtmlFetcher / HtmlFetcher | 保留 HTML + 最终 URL、正文就绪、30 秒等待、人工验证后续读；获取方式替换为内置 WebView   |
| BaseAdapter.collect              | 保留相对分页、去片段防循环、最多 30 页、合并原文；增加停止原因和完整性                  |
| BaiduAdapter                     | 保留标题、作者、正文选择器，以及注释、举报按钮和原有属性清理规则                        |
| BackendClient.format             | 保留 HTML 清理、FormatContent、段落/图片追加换行、后台简介和主图基底；复用当前 CMS 登录 |
| AiMetadata                       | 保留严格类型、简介 130 字符、标签 3～5 个、分类 ID 白名单和逐字段回退                   |
| AiLayout                         | 保留片段编号、顺序/覆盖校验、图注处理、允许的首尾清理、一次纠正与原文回退               |
| _paginate                        | 保留 240/280/100 数值、段落偏好、尾页平衡和原分页标记                                   |
| payload_for / submit             | 保留字段及 tags 在提交边界字符串化，使用旧普通模式的自动提交终点                        |
| ArticleWorkflow                  | 保留采集→格式化→元数据→整理/分页→提交顺序，增加本地任务、队列和状态持久化               |

AI 元数据仍读取原始标题和正文纯文本，只覆盖合法的启用字段。简介失败保留后台简介，分类失败保持默认 `1`，标签失败保持空数组；一个字段失败不影响其他有效字段。[A4]

分类 ID/名称冲突仍是接入前核对事项：以真实后台分类含义生成提示词，不能把目前可能错误的名称表照搬。默认 ID 和逐字段回退的整体行为尽量保留。

正文整理继续允许清理连续位于首尾的独立推广/署名块及指定图注装饰、图源尾注；不是零删字模式。正文顺序、文字片段和图片覆盖按旧规则校验，原始素材独立保存。[A3]

完整 AI 结果校验失败最多纠正一次；网络失败、截断、再次失败或不支持结构时回退处理前正文，并继续原有后续提交逻辑。两项同时开启而整理失败时整体回退，不另跑一套不同布局的补救分页。

来源分页始终负责采全原文，不受“自动内容分页”开关影响。来源页失败、取消验证或达到页数上限仍有下一页时，记录失败/不完整，不自动提交残缺文章；可从状态格重试，不插入预览页面。

这轮新增的是持久串行队列和历史；不同时加入批量粘贴、并发爬取、通用网站识别、图片离线归档或自动创建渠道素材。

## 7. 正文整理与内容分页保持独立

旧 `AiLayout._render()` 内部直接调用 `_paginate()`，原来的一个开关同时控制整理和分页。这里必须做最小拆分，才能支持你要求的两个独立设置；分页算法本身继续复用。[A3]

| 正文整理 | 内容分页 | 执行行为                                                                    | 本步 AI 请求                             |
| -------- | -------- | --------------------------------------------------------------------------- | ---------------------------------------- |
| 关闭     | 关闭     | 使用后台格式化正文，不整理、不新增分页                                      | 0                                        |
| 开启     | 关闭     | AI 输出布局并通过原文引用校验后渲染，直接连接语义组，不运行分页算法         | 通常 1 次，完整结果校验失败最多纠正 1 次 |
| 关闭     | 开启     | 从现有 HTML 提取不可拆的原段落及图文组，保留各组 HTML，仅运行原本地分页算法 | 0                                        |
| 开启     | 开启     | 沿用旧流程：AI 整理 → 保真校验 → 语义组分页 → HTML 输出                     | 通常 1 次，完整结果校验失败最多纠正 1 次 |

“只分页”的必要适配：

- 不经过会重建段落和清理图注的 AI 渲染路径，避免关闭整理却仍修改正文。
- 将原段落视为默认不可拆组；图片与明确图注绑定，按原相邻关系归组，不使用 AI 猜测语义，不复制图片。
- 对结构不明或无法安全分组的内容保留原文并提示跳过分页，不能为了满足页长把文字或图片丢掉。
- 超长原段落允许超过目标页长；不开整理时，不承诺获得与 AI 语义分组完全相同的分页位置。

沿用的排版分页数值和契约：[A3]

- 整理段落目标 1～2 句、40～100 字。
- 分页目标 240 字，全文不超过 280 字时单页，尾页不足 100 字时平衡最后两页或合并。
- 相同字数偏差时优先 3～4 段，再选较早边界；正文计数忽略空白，图注与来源不计入。
- 图片与图注同页，按原顺序各出现一次；来源行放全文最后。
- 最终仍是一个 `newsText` HTML，以 `[!--empirenews.page--]` 分页。

开关仅控制本篇后台任务，不追溯改写历史记录或已提交文章。新采集时两项关闭保留后台返回的 HTML；整理开启时沿用旧逻辑重建布局，不启用分页就不产生新的分页标记。任务处理完成后直接进入 CMS 提交，不增加预览或确认页面。

## 8. 内置 WebView 的实现边界

### 8.1 结论：可以，当前锁定版本已经提供所需接口

PressDock 的 `src-tauri/Cargo.lock` 当前锁定 `tauri 2.12.5`。已经对照该版本本地依赖源码，并通过 `ego-browser` 查阅官方文档：[T1]～[T5]。

| 需要的能力           | 当前接口                                        | 本计划中的用途                                                        |
| -------------------- | ----------------------------------------------- | --------------------------------------------------------------------- |
| 打开外部网页         | `WebviewWindowBuilder` + `WebviewUrl::External` | 创建应用管理的来源采集窗口                                            |
| 监听导航和页面加载   | `on_navigation`、`on_page_load`                 | 跟踪重定向和页面生命周期                                              |
| 执行脚本并取回结果   | `eval_with_callback`                            | 读取当前 URL、readyState 和渲染后 HTML，结果直接回到 Rust             |
| 保留浏览器会话       | WebView 数据目录 / 数据存储                     | 在采集 WebView 内登录来源网站，并按平台能力持久保存                   |
| 必要时执行初始化脚本 | `initialization_script`                         | 可用于初始化观察逻辑；首期优先使用 Rust 发起的 DOM 读取，减少注入逻辑 |

**不需要让来源网页调用 Tauri `invoke` 来回传正文。** Rust 对指定采集 WebView 执行脚本，原生回调接收 JSON 结果，再由可信业务层解析。官方说明 `eval_with_callback` 会将求值结果序列化为 JSON 字符串；普通 `eval` 只执行脚本，不提供同样的结果回调。[T1]

页面 `load` 完成不代表异步正文已经出现。因此继续沿用 ArticleHarvest 的“以站点正文提取规则判断就绪”行为，默认等待 30 秒；需要登录或验证时显示来源页面，完成后重新读取当前页。[A1]

### 8.2 建议的窗口形式

| 形式                               | 可行性和代价                                                                                              | 本版建议                         |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 应用内独立采集窗口 `WebviewWindow` | 使用常规窗口 API，远程页面与工作台分开；仍是 PressDock 管理的内部 WebView                                 | 首期采用                         |
| 主窗口右侧真正嵌入第二个 WebView   | 当前 `Window::add_child` 属于 multiwebview，需要 `unstable` Cargo feature，并处理尺寸、位置和窗口生命周期 | 如你明确希望同窗展示，再选此方案 |

独立采集窗口由应用后台任务管理，不启动系统 Chrome/Edge。素材导入页负责入队和两列状态展示；来源窗口用于实际网页加载，只有需要登录或验证码时才引导用户操作。后台可保存多个排队链接，但只用一个 worker 和一个采集 WebView 串行执行，不先建设多标签和并发浏览器管理器。[T2][A2]

正常采集建议不抢占工作台焦点。是否能全程隐藏来源窗口，需要阶段 1 实测 Windows/macOS 下的页面加载和后台节流；如验证需要显示，则显示来源网页供用户操作，不增加文章结果预览。

首期不采用 React iframe 嵌入来源网页，避免把跨站 DOM 读取建立在 iframe 上；当前应用 CSP 本身也禁用了 frame。

### 8.3 平台与登录状态边界

- **Windows：**Tauri 使用 WebView2，可为采集窗口配置稳定的数据目录。[T3][T4]
- **macOS：**Tauri 使用 WKWebView。官方提供的独立 `data_store_identifier` 需要 macOS 14 及以上，不能把 Windows 的目录方案直接等同复制到 WKWebView。[T3][T4]
- 基于不同引擎和独立数据存储，不能承诺直接复用日常 Chrome/Edge 的登录状态。来源网站需在采集窗口内登录；是否能重启恢复，要用选定的平台存储方案验证。
- 若需要支持 macOS 14 以下版本，需验证默认持久数据存储是否满足需求，或补充原生实现；目前不承诺其具有相同的独立采集 profile 能力。
- 内置 WebView 具备页面渲染和 DOM 读取能力，但具体站点是否允许嵌入式浏览器登录、能否通过验证，仍需代表链接实测。

外部 Chrome/Edge CDP 仍可作为以后复用日常浏览器登录状态的兼容方向；本版先实现内置 WebView，不默认同时重做全部 HTTP/CDP 模式，也不在失败时静默切换模式。

### 8.4 采集页与业务权限隔离

当前 `default.json` 的业务权限只授予 `main`。新增采集窗口使用不同 label，来源站点不获得 CMS、AI、数据库或文件系统命令权限；不新增面向来源站点的 `remote.urls` 业务能力。Tauri 官方说明，远程内容访问命令需要显式 capability 配置。[T5]

脚本读取由 Rust 发起；回调结果核对任务、当前导航和来源 URL，取消、跳转或会话变化后丢弃旧结果。Windows 对求值异常的回传有限制，读取脚本需将异常显式包装为结果，同时保留原生回调超时处理。[T1]

## 9. CMS 自动提交及结果判定

沿用旧后台契约：[A5]

- 格式化：`POST /api/Util/FormatContent`，输入顶层 `content`，读取顶层 `content`、`titlePic`、`smallText` 和 `msg`。
- 创建文章：`POST /api/Article`。
- payload：`title`、`newsText`、`writer`、`titlePic`、`sourceUrl`、`smallText`、`classId`、`tags`。
- `tags` 在内部为数组，提交时才序列化为紧凑 JSON 数组字符串；不使用大写 `Tags` 或直接传数组。

采用旧正常模式的自动提交行为。当前产品流程中不暴露 `submit=False` 的预览出口，也不增加预览控件；更不以“进入编辑”作为采集后的必经步骤。

提交前保存最终 payload 和“提交 CMS 中”状态，只有明确成功响应才写“已添加到 CMS”。接口实际返回远端文章 ID 时再记录，不编造 ID 或文章地址，也不把后台接受等同于已经正式发布。

网络超时、连接中断、成功响应解析不完整、请求发出后的取消，或者应用在远端成功与本地记账之间退出，都可能导致结果未知。这些任务进入“提交结果待确认”，不自动重发；核对方式依真实 CMS 查询契约确定。

FormatContent 失败、原文采集不完整或用户取消时不提交；AI 字段/整理失败按既有规则降级并携带本地警告，可以继续提交。不自动重试付费请求或创建文章的写请求。

实现已接入现有 CMS 会话和上述接口；本轮未运行真实采集、CMS 登录或线上文章创建，接口及站点兼容性仍需实机联调。

这些是实施验收要求，不代表本次已经运行或新增测试。实现时遵循仓库约定；浏览器观察和 Web 验收使用 `ego-browser`，开发服务器须有授权才能启动。
