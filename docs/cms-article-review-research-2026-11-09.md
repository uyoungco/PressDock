# CMS 一、二、三级文章审核调研

调研时间：2026-11-09（北京时间）。入口：[一级待审核文章](https://newsadmin.nccontrol.com.cn/index.html#/article/article-review-0)。使用 ego-browser 复用已有登录，只调研交互、真实查询和被拦截的审核请求，未实现审核功能。

## 结论与验证范围

三页共用 `ArticleReview` 前端组件及文章更新接口。单条审核与批量审核都使用 **`PUT /api/Article/{id}`**，通过 `action` 区分同意和拒绝。批量是对勾选记录逐篇请求，没有发现独立批量审核接口。

| 页面       | 原站路由                    | 列表查询 `status` | 本次真实查询           | 已验证内容                                           |
| ---------- | --------------------------- | ----------------- | ---------------------- | ---------------------------------------------------- |
| 一级待审核 | `/article/article-review-0` | `0`               | 47021 条，当前页 50 条 | 单条同意/拒绝、选择两篇批量同意/拒绝，均在发送前拦截 |
| 二级待审核 | `/article/article-review-1` | `1`               | 0 条                   | 真实空列表、批量弹层与拒绝原因弹框；取消操作         |
| 三级待审核 | `/article/article-review-2` | `2`               | 0 条                   | 真实空列表、批量弹层与通过确认框；取消操作           |

二、三级单条审核和有选中记录的批量审核由共用组件源码确认，**没有真实记录可供抓取这两级的提交参数**。没有构造线上记录、修改文章级别或注入假数据填充空列表。

在首次点击审核前，给本次标签页的 XHR 和 fetch 加入写请求阻断：非 GET/HEAD/OPTIONS 请求在原始网络发送函数之前终止，不返回伪造成功结果。一级共捕获并阻断 **6 次 PUT**：单条同意 1 次、单条拒绝 1 次、批量同意 2 次、批量拒绝 2 次。最后只读复查的一级详情 `Status` 仍为 `0`。调研没有向服务器发送审核写请求。

[脱敏证据](evidence/cms-article-review-2026-11-09.json)保存查询响应的结构、列表数量、被阻断请求的字段名和源码文件 SHA-256，不保存令牌、账号资料、文章标题、正文或真实文章 ID。

## 查询、详情与身份认证

三页列表调用同一个接口，实测查询格式如下，`status` 分别替换为 0、1、2：

```http
GET /api/Article?status=0&current=1&pagesize=50&priority=0&editor=0&nubia=0&quality=0
```

三页本次查询均为 HTTP 200，响应包括 `data/total/current/pageSize/msg`，`msg="succ"`；还有 `recommand/promote` 等字段。一级可筛选作者及 editor，二、三级隐藏这两个筛选。分类、ID、标题、起止时间和每页条数沿用现有文章查询能力。

点击单条“审核”后，先调用 `GET /api/Article/{id}`，响应是 `{ data, log, msg }`。`data` 包含 PascalCase 的文章字段、`NewsText`、`Status`、`UpdatedAt`、`Tags/NTags` 等。本次脱敏摘要仅记录详情 Tags 的 `typeof` 为 object，未区分 null、数组等具体形态，不能据此判断其业务类型。

原站 Axios 使用同源地址、`Content-Type: application/json;charset=utf-8`、180000 毫秒超时，通过请求拦截器填充 `Authorization`。其登录流程把 `tokenType` 与 `accessToken` 拼成认证值。本项目继续复用 Rust CMS 会话和凭据库，不复制原站把令牌存入 localStorage 的方式。普通页面 fetch 不经过原站 Axios 的认证拦截器，不能直接当作已认证 API 客户端使用。

## 单条审核交互与请求

1. 点击行内“审核”，打开右侧宽 1200 的审核抽屉并读取详情。
2. 抽屉展示标题与 HTML 正文，底部提供“拒绝”“同意”；不是文章编辑表单。点击遮罩不关闭抽屉，右上角可关闭。
3. 同意打开二次确认：`是否确认通过审核？`，按钮为“确定 / 取消”。
4. 拒绝打开原因输入框：`是否拒绝通过审核？请输入原因。`，按钮为“确定 / 取消”。
5. 确定后调用同一文章 PUT。原站单条路径等待该请求，再提示成功，约 500 毫秒后关闭抽屉并刷新列表。

审核接口通过业务动作处理，实测请求**不包含 `status` 或 `Status`**，也不携带“目标审核级别”：

| 审核决定 | `action`   | `comment`      |
| -------- | ---------- | -------------- |
| 同意     | `"accept"` | `""`           |
| 拒绝     | `"reject"` | 输入的拒绝原因 |

被拦截的单条请求字段为：

```text
id, newsText, title, classId, className, writer,
titlePic, titlePic2, titlePic3, smallText, sourceUrl,
action, comment
```

它使用 **camelCase**，ID 同时出现在路径与 `id` 中，两者一致。请求带详情转换后的正文与元数据，不是仅 `{ id, action, comment }`。服务端是否接受最小请求体，本次没有验证，后续不能据此省略这些字段。

源码会对 `tags` 执行 JSON.stringify，但打开审核抽屉时并未从详情填入 tags；本次单条同意与拒绝的实际序列化请求均**没有 `tags`**，也没有 `nTags/NTags`。不能把“字段缺省”自行替换为“发送空数组字符串”，否则可能造成标签丢失。

另一个需要避免的原站行为：详情 `NewsText` 先经过图片显示辅助函数，为 `<img>` 增加 `max-width:100%;height:auto;`，随后把这个显示用 HTML 放入提交对象。因此“仅审核”也可能携带经过显示处理的正文。PressDock 后续应将预览 HTML 与原始 HTML 分离，审核时保留原文，不能提交预览 DOM 或编辑器重新序列化的正文。服务端是否实际更新这些附带字段，仍需独立验证。

## 批量审核交互与请求

1. 表格支持逐行勾选与表头全选，组件维护选中行数组；不是提交全部搜索结果。
2. 顶部“审核”打开小型弹层，文字为 `是否审核通过?`，提供“关闭 / 拒绝 / 同意”。
3. 同意和拒绝分别进入与单条相同的确认框、原因输入框。
4. 确定后遍历选中行，每篇执行一次 `PUT /api/Article/{id}`；同一批拒绝共用一条原因。

被拦截的每篇批量请求字段为：

```text
Id, Title, ClassId, ClassName, TitlePic, SourceUrl, NewsTime,
TitlePic2, TitlePic3, SmallText, Tags, Writer, Pages, NTags,
commentRecommand, commentPromote, action, comment
```

批量请求使用 **PascalCase 列表行快照**，不是单条审核请求体。`action/comment` 和两个展示派生字段仍是 camelCase。请求不包含 `NewsText`、`newsText`、`Status`、`status`，也没有在提交前逐条读取详情。

列表加载时，原站将 Tags/NTags 的 JSON 字符串解析成数组，将 null 转为空数组；提交时再对这两个字段 JSON.stringify。因此批量请求中 `Tags/NTags` 是 **JSON 数组字符串**，例如 `"[]"`，不是数组。`commentPromote` 保持数组，`commentRecommand` 为字符串；二者是前端从列表附带的分发数据派生的字段。

本次选择两篇并同意，捕获两次 PUT；重新选择同样两篇并拒绝，又捕获两次 PUT。没有使用逗号连接 ID、ID 数组或其他批量接口。

### 原站批量处理的问题

- **没有等待真实请求结果。** 源码采用 `Promise.all(selected.map(async row => { update(row) }))`，回调中没有 await 或 return `update` 的 Promise。外层 Promise.all 很快结束，随后提示“操作成功”并安排刷新。调研中，PUT 已被阻断，原站仍执行列表刷新并清掉选择；不能把这种提示作为服务器审核成功的证据。
- **没有空选校验。** 批量审核入口及其处理函数没有检查选中数。空数组也会走确认、提示成功和刷新路径。应在 PressDock 中禁用空选入口并再次校验。
- **没有逐篇结果。** 源码并发发出请求，未限制并发、未收集失败、未区分部分成功，也没有发现幂等键。
- **拒绝原因缺少前端规则。** prompt 没有配置必填、长度或空白校验。本次非空原因请求已被拦截；空白原因是否被服务端拒绝没有验证。项目可增加非空校验，但不能编造后端字数上限。

## 三级差异、权限和未确定行为

共用组件以路由最后一位决定列表 status，审核函数不根据 0/1/2 分支构造动作。三个级别的同意均提交 `accept`，拒绝均提交 `reject`。不要把页面查询的 status 当成审核 PUT 的目标状态发送。

| 项目           | 已有证据                                                                | 后续仍需核验                                            |
| -------------- | ----------------------------------------------------------------------- | ------------------------------------------------------- |
| 各级请求动作   | 三页共用同一函数，accept/reject 不随级别改变                            | 二、三级有真实待审记录时的请求与服务端结果              |
| 状态变化       | 查询映射 0/1/2 已由真实响应确认                                         | accept 是否逐级推进、能否跨级；reject 的落库状态        |
| 三级通过与发布 | 路由和共用组件包含 status=3 的已审核展示逻辑                            | 三级通过是否立即发布、生成静态页、同步渠道或有延迟      |
| 返回与成功条件 | 原站主要按 HTTP 200/204 处理公共响应；真实只读响应 msg=succ             | 审核写响应的准确结构、业务错误、并发冲突                |
| 数据覆盖       | 单条携带正文/元数据，批量携带列表元数据                                 | 后端对 accept/reject 的附带字段是否更新、是否有版本校验 |
| 权限           | 原站 `role.includes("editor")` 时隐藏单条及批量审核；当前会话可看到入口 | 每一级的后端角色/权限要求；隐藏按钮不等于服务端鉴权规则 |

前端没有发现审核前发送版本前置条件，也没有发现下一状态、撤回或回滚协议。不能假定 `accept` 的效果就是数值加一，不能自行设计拒绝状态值或声称三级通过已经发布成功。

一级额外有“优先审核”，其独立函数调用 `POST /api/priorityData`，请求体 `{ id }`。这是另一个动作，本次没有点击提交或发送，不能与审核同意混用。二、三级没有该按钮。

## PressDock 后续实现建议

以下是待实施方案，不代表现有功能或已确认的新增服务器接口。

### 接入位置与协议边界

- UI：`src/pages/Articles/index.tsx`、`src/pages/Articles/MobileArticles.tsx`、`src/features/cms-articles/ArticleTable.tsx`。新增选择、批量工具条与独立审核预览，审核决定不自动保存未提交的编辑稿。
- 业务与类型：`src/features/cms-articles/service.ts`、`src/types/cms-article.ts`。审核决定限定为 accept/reject；待审页面限定为 review-1/review-2/review-3，明确排除 quality。
- IPC：`src/services/tauri/articles.ts`。建议新增专用审核命令，命令名在实施时确定，同时注册 Rust handler 和最小 Tauri ACL；组件不直接 invoke 或请求 CMS。
- Rust：`src-tauri/src/commands/cms.rs`、`src-tauri/src/cms/article_management.rs`。复用会话、认证失效、图片许可及写入错误处理。现有 `cms_update_article` 固定 `action="edit"`，不要把它改成可透传任意 action 的通用接口。
- 分别构造已观察到的单条和批量请求体。现有 `CmsArticleRow.snapshot` 可作为批量编码依据，注意只序列化一次 Tags/NTags；单条保留详情的原始 HTML，不混入预览样式。最小请求体或统一大小写协议需先有独立证据。

### 提交、刷新和异常

1. 确认时展示所选数量、审核决定及拒绝原因，冻结本次 ID 和数据快照。当前页选择、换筛选/翻页清理选择即可作为首版，不增加未经确认的“全部结果审核”。
2. Rust 可在提交前只读核对实际状态与页面是否匹配；不匹配则停止该篇并提示刷新。这只能减少过期操作，没有服务端条件更新协议时不能消除检查后的竞态。
3. 从串行逐篇提交开始，每篇完整 await，返回逐篇成功、失败、结果待确认和未执行情况；单次批量不是数据库事务，不承诺整体回滚。
4. 防止重复点击。明确成功才移除已完成选择；失败保留供核对。提交后使相关审核页、详情及优质文章等受影响缓存失效，并重新查询当前页。当前页清空时重新读取并调整页码。
5. 复用 401/A0230 会话失效流程，403 保留会话。超时、断连和响应不明确提示“结果未确认，请刷新核对”，不自动重试。身份或权限变化时停止尚未发送的批次；已经发送的请求不能声称被撤销。
6. 现有 Rust 写服务以 `msg="succ"` 确认其他文章写操作，可复用其错误封装；但审核写响应尚未验证，接入时不要把 HTTP 成功直接等同于业务成功，也不要伪造发布结果。

### 后续验收

先使用明确标识的本地演示数据和本地 HTTP 服务验证参数、同意/拒绝、空选、重复点击、部分失败、会话失效、结果待确认和分页/缓存更新；不得把这些结果显示为真实审核成功。正文和标签需要覆盖原样保留、null、空数组字符串、带标签和图片样式等场景。

二、三级真实记录、服务端状态迁移、审核写响应、权限及三级发布效果，仍需另行授权的测试记录做完整验证；本次不修改真实数据以补齐这些结论。
