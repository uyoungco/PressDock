# PressDock 新闻首页工作流评估

日期：2026-10-28

## 评估范围

本报告以你的实际工作为主线：在百度寻找素材，导入 CMS，人工调整正文、插图和分页，再添加到渠道素材，为不同位置处理渠道标题和图片。依据当前仓库代码、README 和现有接口说明，评估可以减少重复操作的功能。

本次仅做静态代码分析，没有启动开发服务器、打开网站、登录 CMS、实际写入线上数据或验证真实展示。代码已有实现不等于本次已验证线上效果；特别是文章编辑和转渠道的接口文档说明，线上写入尚未用测试数据实写验收。

## 一、主要结论

最值得优先开发的不是另一个独立工具，而是围绕同一篇文章，把正文分页、渠道标题和渠道图片处理变成连续操作。

建议首先解决四件事：

1. **正文分页助手**：在文章编辑器中看到每页内容，快速插入、调整分页点，复用现有自动分页能力生成可修改的初稿。
2. **渠道标题规则**：按渠道和子渠道显示字数上限、实时计数，并让 AI 标题候选使用相同限制；渠道标题与正文文章标题始终分开。
3. **渠道图片检查与复用**：在编辑时直接看到图片、规格及是否符合当前子渠道要求；从文章配图或同一原图生成所需规格。
4. **编辑防丢失和流程衔接**：为未提交的正文提供可恢复的本地草稿；导入完成后尽量直接找到并编辑对应 CMS 文章。

这些建议的价值首先体现在少切换页面、少数标题字数、少重复裁图和降低返工。分页能否增加有效阅读、广告曝光和收益，仍需要真实数据验证，不能只看生成了多少页。

## 四、重点功能方案

### 4.1 正文分页助手

**你的场景**：正文中需要增加分页，但翻页位置还要考虑段落完整性、上下文和配图。当前编辑器会保留 `[!--empirenews.page--]` 标记，但没有专门的分页交互。

建议在文章正文附近提供：

- 当前页数、每页文字量与图片数量；点击页码直接定位到正文对应位置。
- 在当前段落边界插入或删除分页点，直观看到分页位置；支持合并相邻页。
- 一键根据当前编辑稿生成分页初稿，结果先预览，确认后再应用，并可撤销。
- 标出空页、明显短页和可能分离的图片/图注；提示供人工判断，不直接删除内容。
- 保存前检查分页标记是否完整，保存后重新读取 CMS 文章，核对图文和分页是否保持一致。

现有采集算法以约 240 个非空白字符为目标，剩余不超过 280 字时可合并为一页，尾页小于 100 字时尝试调整。它按语义组或原段落切分，长段落可能超过目标；这些值是当前算法偏好，并非适用于所有文章的硬性标准。现有逻辑位于 [分页算法](../src-tauri/src/harvest/layout.rs) 和 [采集处理流程](../src-tauri/src/harvest/worker.rs)，需要适配到正在编辑的正文，并处理已有分页点和不同 HTML 结构，不能直接假定原算法可无损处理所有文章。

第一版可以先实现手动插入/删除、页数和逐页预览，再加入自动初稿。图文页的合适长度可用真实文章试用后再定；不建议为了制造页数而把紧密相关的句子或图注拆开。

### 4.2 渠道标题规则

**你的场景**：渠道标题不是正文标题，不同渠道位置限制字数，人工反复数标题容易返工。

建议在现有子渠道图片预设旁维护标题要求：

- 选择子渠道后显示“当前字数 / 上限”，超出时指出超出数量。
- 手输、粘贴、AI 候选和保存前检查采用同一套计数规则；未配置时明确显示“未配置”，不猜上限。
- AI 优化默认带入该子渠道上限，允许人工选择候选，仍需核对事实。
- 修改子渠道时保留当前标题并重新检查；不要自动截断，也不要改动文章正文标题。
- 将表单的 `Title`、`TitlePic` 等名称补充为“渠道标题”“渠道主图”等业务名称，降低填写成本。

当前 AI 候选以 Unicode 字符计数，标点计入。真实渠道是否对中英文、空格、标点或特殊字符采用不同规则，需要以渠道实际要求为准。

### 4.3 渠道图片检查与复用

**你的场景**：渠道对图片文件体积和像素尺寸有要求，找好图片后还需要反复处理。

建议先做一个紧贴现有表单的改进：

1. 显示 `TitlePic`、`TitlePic2` 的当前图片，以及目标尺寸、体积和格式。
2. 对从文章带入、手填或切换渠道后保留的图片，按可获取的实际数据重新检查；显示“符合 / 不符合 / 待检查”。
3. 不符合时提供直接重新裁剪处理的入口；处理完成后仍由你确认上传和保存素材。
4. 读取失败或外部地址不允许访问时，保留“待检查”，不要把未知当成合格。

随后再做“选一次原图，生成多个规格”：为每个目标保留独立裁剪框，从原图分别生成，并展示实际尺寸和文件大小。正文大图与渠道缩略图分开保存，避免为了缩略图而缩小正文图。当前处理器和子渠道预设可复用，但现有处理流程是一次处理一个图片字段，不能直接假定已经具备多规格编排。

### 4.4 找图后的正文配图工作流

现有正文编辑器已经有图片上传；真正值得缩短的是“搜到图以后”的步骤。

- 在当前文章中集中收集已选图片，支持选择本地文件或粘贴剪贴板图片；上传后插入光标位置，并显示来源信息和使用状态。
- 若复制的是网页图片链接而非图片文件，应先明确该图片能否读取和上传，不能把临时外链直接视为已保存的配图。
- 从图片栏插入正文光标位置，或选择正文已有图片作为渠道图的原图。
- 对需要不同规格的渠道图继续走现有裁剪、压缩和上传流程。
- 保留必要的来源页面、作者或授权备注，方便后续核对。

首版不必接入复杂的图片搜索服务。可先保留你熟悉的搜索引擎找图方式，重点减少找到图后的保存、上传、重复选择和裁剪。正文图片是否能直接作为渠道图原图，以及远程图片能否安全读取，需要结合现有图片许可和实际素材验证。

### 4.5 草稿恢复与覆盖提醒

当前真实文章编辑的未保存修改仅放在运行内存；同账号会话失效后可恢复，但显式退出、换账号或关闭应用会清空。正文处理越久，意外中断造成的返工越大。

建议增加按账号和 CMS 文章 ID 关联的本地草稿，自动保存未提交修改，重新进入时由你决定恢复或丢弃。界面应区分“本地草稿已保存”和“CMS 已保存”，不能把前者显示成远端已更新。原始采集内容保持独立，不因保存草稿被覆盖。

如果编辑期间 CMS 中的文章可能被其他人或其他页面修改，恢复或提交前应比较可获得的更新时间或内容快照；有差异时提示并让你选择处理方式。`updatedAt` 的可靠性及 CMS 是否支持真正的并发控制仍需核实，单靠客户端检查不能保证完全避免并发覆盖。

### 4.6 从导入到编辑，再到渠道

理想的日常操作可以是：

```text
搜索并选择文章 → 粘贴链接导入 → 打开对应 CMS 文章
→ 整理段落、插图、分页 → 保存文章 → 添加到渠道素材
→ 检查渠道标题和图片 → 保存素材 → 核对实际展示
```

现有文章列表已经有“添加到渠道素材”，并带入标题、两图、摘要和作者，不需要重新设计这一入口。可以改善的是：

- 导入记录在拿到可靠 CMS 文章 ID 时，增加定位或打开该文章的操作。
- 若创建响应没有 ID，允许按可验证信息辅助查找并由人确认；不要根据相似标题猜测关联。
- 文章编辑保存后提供明确的下一步入口；仅在符合现有“优质文章可添加”的条件时使用真实转渠道协议。
- 渠道素材的新增和文章转素材使用不同的现有请求语义；不要用普通新增代替文章关联。
- 文章保存成功、渠道素材保存成功、实际首页展示分别显示，不能混成一个“已发布”。

普通渠道列表的新增表单目前从空值开始，且渠道、子渠道使用文本输入。可以复用筛选区已有的真实渠道配置，默认带入已提交的渠道、子渠道和日期，并允许修改；文章转素材表单已经使用真实选择器，不应再重复开发。

## 五、其他可选方向

### 5.1 今日工作清单

以采集任务和真实 CMS 结果为基础，列出“等待编辑、编辑中、等待渠道适配、渠道素材已保存、展示待核对”等状态，并提供继续处理入口。状态应附有来源和更新时间；暂时无法从 CMS 确认的部分应标为人工记录或待核对。

现有工作台的稿件统计和发布页面包含本地历史或演示数据；不能直接将其数字解释为当天真实 CMS 工作量或线上发布量。工作台中的“真实采集尚未接入”文案也与目前采集代码不一致，后续更新工作台时应同步纠正。

### 5.2 批量链接和重复提示

如果你习惯先搜集多个链接，可以一次粘贴多行，逐条提示格式错误、已有采集记录，再交给现有队列处理。现有队列已经支持连续单条入队，不需要为了批量入口先增加并发。

当前去重主要基于账号、规范化后的来源 URL 和任务模式，不能保证识别不同地址的转载或同一内容。跨地址相似内容最多提示人工核对，不应自动判定重复并跳过。

### 5.3 多渠道版本与首页预览

如果同一篇文章经常进入多个位置，可以做一张适配表，按行显示渠道、子渠道、渠道标题、图片规格和保存结果。文章正文仍是一份，渠道标题和图片各自独立。

渠道组合预览可以展示多条素材的标题换行和图片裁切，帮助发现相邻标题雷同或重复配图。但预览是否与线上一致取决于真实位置尺寸、字体、裁切规则和排序语义；未核实前只能标为近似预览。现有排序仅提交当前页，不能直接视为完整首页排版。

## 六、如何判断分页是否真正带来收益

分页可能增加每次访问产生的页面浏览，但页数增加不等于读者一定翻页，也不等于广告收益一定增加。可以围绕同一题材、渠道和位置，观察：

| 指标                               | 用途               | 注意事项                                     |
| ---------------------------------- | ------------------ | -------------------------------------------- |
| 首次进入文章的会话数或访客数       | 看入口规模是否相近 | 统一统计口径和时间窗口                       |
| 各页到达率、第二页及后续页比例     | 看读者是否继续阅读 | 需能区分真实页码和重复刷新                   |
| 每次文章会话的 PV、阅读完成情况    | 看阅读深度与体验   | 页数上升但后续页流失也要同时观察             |
| 广告有效曝光、收入及每千次会话收入 | 看业务结果         | 取广告平台的真实口径，不把页面 PV 当广告曝光 |
| 标题/图片的入口曝光与点击率        | 看渠道素材效果     | 需能区分渠道、位置和时间                     |

先记录一段时间的现有结果，再在流量条件尽可能相近的文章或可控分组中比较不同分页方式，按渠道、位置、设备和题材分组。若平台没有这些字段，需要先确认可用的统计报表或数据接口；当前仓库没有发现现成的访问分析和广告收益接入，不能凭分页数估算收入。

## 七、建议实施顺序

1. **先做低依赖的日常提效**：渠道标题规则与字数提示；普通渠道新增沿用已提交筛选并使用真实选择器；正文分页点插入、删除和页数提示。
2. **补足正文处理闭环**：逐页预览、在当前编辑稿上生成分页初稿、本地草稿恢复和远端修改提醒。用真实文章验证分页标记、图文顺序及 CMS 往返。
3. **减少图片和页面切换**：渠道图片预览与规则检查、导入后定位文章、正文图片复用；根据使用频率再做一图多规格和多渠道适配表。
4. **最后做效果复盘**：在确认统计与广告数据来源后接入真实指标，再评估分页策略和渠道标题图片的效果。

各阶段都可以独立交付；无需先更换 CMS 或重新实现现有采集、图片处理、AI 标题和渠道操作。

## 八、开发前最有价值的确认

1. 常用的渠道和子渠道有哪些？每个位置的标题上限、计数规则、两张图的尺寸和体积要求分别是什么？
2. 一篇文章通常需要分成几页？你目前如何判断分页位置，图文文章和纯文字文章是否有不同习惯？
3. 找图后通常使用复制图片、下载文件，还是复制图片链接？是否需要记录图片来源或授权信息？
4. 一篇文章平均会添加到几个渠道位置？渠道素材保存之后，还需要做哪些首页排序或上线核对？
5. 是否有现成的访问统计和广告报表，能按文章、渠道位置、页码查看阅读与收益？

这些答案会决定标题规则、分页默认策略、图片复用和数据复盘的具体范围；在确认之前，上述方案属于基于代码与现有描述的产品建议。
